  2. Arquitectura propuesta

   [Página web] ──┐
                  ├── HTTP/JSON ──► [Spring Boot]
   [Extensión]  ──┘                   ├─ api/        LinkController (REST
  /api/...)
                                      ├─ web/        RedirectController (GET
  /{alias})
                                      ├─ service/    LinkService (lógica de
  negocio)
                                      ├─ alias/      AliasGenerator (interfaz) +
  implementación
                                      ├─ qr/         QrCodeService (genera el
  QR)
                                      ├─ domain/     Link (@Entity)
                                      └─ config/     propiedades (baseUrl, ttl),
  CORS, Clock
                                            │ EntityManager + JPQL
                                         [HSQLDB en modo archivo → database/]

  - Backend: un solo módulo Spring Boot. Los controllers solo traducen HTTP a
    llamadas al servicio. Las reglas RN1 a RN5 viven en LinkService.
  - Persistencia: HSQLDB en modo archivo dentro de database/, así los datos
    sobreviven a un reinicio. Los tests usan HSQLDB en memoria. LinkService usa
    EntityManager y JPQL directamente, como pediste.
  - Interfaz web: HTML, CSS y JavaScript sin framework, servidos por Spring Boot
    como recursos estáticos. Las fuentes quedan en frontend/ y Gradle las copia
    al build. Al ser el mismo origen que la API, no hace falta CORS para la
    web.
  - Extensión: Manifest V3 con un solo código para Chrome y Firefox. Es un popup
    que al abrirse lee la URL de la pestaña activa (permiso activeTab), llama
    al backend y muestra la URL corta, el QR y un botón para copiar. Para que
    pueda llamar al backend hacen falta host_permissions y CORS configurado en
    el backend.
  - QR: propongo generarlo en el backend con la librería ZXing, en un endpoint
    que devuelve un PNG. Así hay una sola implementación y los dos clientes solo
    muestran un <img src=...>. La alternativa sería usar una librería JS en
    cada cliente, pero eso duplica la lógica.
  - Redirección: responder 302 Found, no 301. Un 301 lo cachea el navegador, y
    como el alias vence y se reasigna, el navegador seguiría mandando a la URL
    vieja. Es un punto de diseño importante.

  3. Diseño conceptual

  Modelo de datos mínimo: entidad Link

  ┌─────────────┬────────────────┬─────────────────┐
  │    Campo    │      Tipo      │      Nota       │
  ├─────────────┼────────────────┼─────────────────┤
  │ id          │ Long           │ PK generada     │
  ├─────────────┼────────────────┼─────────────────┤
  │ alias       │ String         │ UNIQUE          │
  ├─────────────┼────────────────┼─────────────────┤
  │ originalUrl │ String (largo) │ URL validada    │
  ├─────────────┼────────────────┼─────────────────┤
  │ createdAt   │ Instant        │                 │
  ├─────────────┼────────────────┼─────────────────┤
  │ expiresAt   │ Instant        │ createdAt + ttl │
  └─────────────┴────────────────┴─────────────────┘

  Guardo expiresAt en lugar de calcularlo en cada consulta. Así las consultas
  son simples y la duración puede cambiar sin migrar datos.

  Responsabilidades

  - LinkController: recibe y valida el DTO de entrada y arma la respuesta.
  - RedirectController: resuelve /{alias} y responde 302, o un error si no
    existe o venció.
  - LinkService: crea, resuelve y aplica las reglas de vigencia y reutilización.
  - AliasGenerator: interfaz para la estrategia de generación. Es un punto de
    extensión barato si más adelante cambia la forma de generar alias.
  - QrCodeService: convierte un texto en una imagen PNG.
  - Clock inyectado: permite testear el vencimiento de 60 minutos sin esperar.
  - @RestControllerAdvice: devuelve los errores en formato estándar
    (ProblemDetail, RFC 7807).
  - Propiedades configurables: app.base-url (por ejemplo
    http://192.168.1.50:8080) y app.link-ttl (60 minutos por defecto).

  Endpoints

  ┌────────┬──────────────────────────┬─────────────────────────────────────┐
  │ Método │           Ruta           │              Respuesta              │
  ├────────┼──────────────────────────┼─────────────────────────────────────┤
  │        │ /api/links con { "url":  │ 201 con { alias, shortUrl,          │
  │ POST   │ "..." }                  │ originalUrl, expiresAt }; 400 si la │
  │        │                          │  URL no es válida                   │
  ├────────┼──────────────────────────┼─────────────────────────────────────┤
  │ GET    │ /{alias}                 │ 302 con Location: originalUrl;      │
  │        │                          │ error si no existe o venció         │
  ├────────┼──────────────────────────┼─────────────────────────────────────┤
  │ GET    │ /api/links/{alias}/qr    │ image/png (solo si se aprueba el QR │
  │        │                          │  en el backend)                     │
  └────────┴──────────────────────────┴─────────────────────────────────────┘

  El contrato se documenta con springdoc-openapi (Swagger UI).

  Flujo para crear un enlace

  1. El cliente manda la URL.
  2. Se valida: tiene que ser absoluta, con esquema http o https y con host.
  3. AliasGenerator propone un alias y se busca si existe.
     - Si no existe, se inserta.
     - Si existe pero está vencido, se reasigna pisando la fila con un UPDATE
       ... WHERE alias = ? AND expiresAt < now, que es atómico.
     - Si existe y está vigente, se genera otro alias y se reintenta hasta N
       veces.
  4. Se devuelve el DTO con la shortUrl armada a partir de app.base-url.

  La restricción UNIQUE sobre el alias protege contra dos creaciones
  simultáneas: si una choca, se reintenta.

  Flujo para redirigir

  1. GET /{alias}.
  2. Se busca el alias con JPQL.
  3. Si existe y expiresAt > now, se responde 302. Si no, se responde con error.

  Vencimiento y reutilización

  Propongo verificación perezosa: el vencimiento se controla al momento de usar
  el enlace, en la redirección y en la creación. No hace falta un proceso en
  segundo plano para que la regla se cumpla. Como opcional se puede sumar una
  limpieza periódica con @Scheduled para borrar filas vencidas, pero la lógica
  no depende de ella.

  Con este modelo, al reasignar un alias se pierde el historial del enlace
  anterior (ver duda D6).

  Sobre no tener capa Repository: por ahora no veo una razón fuerte para
  agregarla. El costo es que LinkService mezcla reglas de negocio con JPQL. Si
  el servicio crece en etapas siguientes, sería el primer refactor a considerar.
  Por ahora lo respeto como pediste.

  B. Decisiones que tomás vos

  B.1 Funcionales: confirmar con el docente en la minuta

  #: D1
  Decisión: Formato del alias
  Mi recomendación: Aleatorio, alfanumérico, sin caracteres ambiguos (0/O,
  1/l/I), largo configurable (empezando en 5)
  Por qué: Un número secuencial deja que cualquiera recorra los enlaces de otros

  probando valores, y estos enlaces pueden apuntar a carpetas privadas de
  Drive. Con solo 60 minutos de vida hay pocos enlaces activos a la vez, así
  que alcanza un alias corto. Que el largo sea configurable lo protege contra
  un cambio futuro.
  ────────────────────────────────────────
  #: D2
  Decisión: Misma URL acortada otra vez
  Mi recomendación: Alias nuevo cada vez, sin renovar el anterior
  Por qué: Es lo más simple: cada pedido tiene sus propios 60 minutos, que es lo

  que dice la consigna. Reusar el alias obligaría a decidir qué hacer si dos
  personas acortan lo mismo.
  ────────────────────────────────────────
  #: D3
  Decisión: Enlace vencido o inexistente
  Mi recomendación: HTTP 404 con una página HTML simple ("enlace no disponible o

  vencido")
  Por qué: Quien abre la URL corta es una persona en un navegador, no otro
  programa. Uso 404 y no 410 ("eliminado para siempre") porque el alias puede
  volver a usarse.
  ────────────────────────────────────────
  #: D4
  Decisión: Acortar una URL que ya es corta
  Mi recomendación: Rechazarla
  Por qué: Evita bucles de redirección.
  ────────────────────────────────────────
  #: D5
  Decisión: Qué es una URL válida
  Mi recomendación: URL absoluta, solo http o https, con host, máximo 2048
  caracteres
  Por qué: Es el criterio habitual y evita guardar textos arbitrarios.
  ────────────────────────────────────────
  #: D6
  Decisión: Historial de enlaces vencidos
  Mi recomendación: Sin historial: al reasignar se reutiliza la fila
  Por qué: La consigna no lo pide y el modelo queda más simple: alias UNIQUE y
  concurrencia segura. Si la Etapa 2 pide historial o estadísticas, es un
  cambio acotado al módulo link.
  ────────────────────────────────────────
  #: D7
  Decisión: Dominio o IP
  Mi recomendación: Una propiedad app.base-url en el backend, y una pantalla de
  opciones en la extensión para indicar la URL del backend
  Por qué: La IP del ejemplo (192.168.1.50) cambia según la red, así que no
  puede
  quedar fija en el código.
  ────────────────────────────────────────
  #: D8
  Decisión: Dónde se genera el QR
  Mi recomendación: En el backend, con la librería ZXing
  Por qué: Hay una sola implementación, se testea con JUnit y cualquier cliente
  futuro la obtiene sin esfuerzo. La consigna dice que los clientes lo
  "generan": hay que confirmar con el docente que este enfoque sea aceptable.
  Si no, la alternativa es una librería JS incluida tanto en frontend/ como en
  extension/.

  C.4 Buenas prácticas

  - REST
    - Recursos en plural (/links).
    - 201 Created con encabezado Location al crear un enlace.
    - 400 si la entrada no es válida, 404 si no existe.
    - 302 (no 301) en la redirección, porque el navegador cachea el 301 y el
      alias se reasigna.
    - Errores en formato ProblemDetail (RFC 9457).
  - Spring
    - Inyección por constructor.
    - @Transactional en el Service, nunca en el Controller.
    - Ninguna lógica de negocio en los Controllers.
    - spring.jpa.open-in-view=false.
  - JPA
    - Fechas con Instant.
    - UNIQUE e índice sobre alias.
    - Las entidades nunca se exponen en la API.
    - JPQL con parámetros nombrados, sin concatenar strings.
    - Reasignación atómica (UPDATE ... WHERE expiresAt < :now).
  - Seguridad básica
    - Validar esquema y largo de la URL (evita guardar javascript: y similares).
    - CORS habilitado solo para el origen de la extensión.
    - Alias aleatorio para que no se puedan recorrer los enlaces de otros.
  - Tests
    - Unitarios del generador de alias y de la lógica de vencimiento, usando un
      Clock fijo.
    - De integración con @SpringBootTest y MockMvc sobre HSQLDB en memoria, uno
      por criterio de aceptación.
    - JaCoCo con un umbral mínimo a acordar.
  - Trabajo con IA
    - Cada incremento parte de una especificación escrita (historia de usuario,
      criterios de aceptación y contrato).
    - El prompt se guarda en docs/etapa-1/prompts/.
    - El código generado se revisa y se prueba antes de aceptarlo.
  - Git
    - Un commit por incremento y un tag por etapa.
    - database/, build/ y .gradle/ en .gitignore.

  Las dos correcciones

  1. CORS en la extensión.
  - En Firefox el origen es moz-extension://<UUID> y ese UUID cambia en cada
    instalación, así que no se puede poner en una lista de orígenes permitidos.
  - Con host_permissions en el manifest, el popup puede llamar al backend sin
    necesidad de CORS, tanto en Chrome como en Firefox.
  - Esto choca con D7. La URL del backend se configura desde la pantalla de
    opciones, así que el host no se conoce de antemano y no puede quedar fijo en
    host_permissions. Propongo usar optional_host_permissions y que la pantalla
    de opciones pida el permiso con permissions.request() al guardar la URL.
    Así se pide permiso solo para ese host, sin abrir http://*/*.
  - Un detalle de Firefox: en MV3, Firefox puede dejar los permisos de host sin
    otorgar hasta que el usuario los acepte. Pedirlos desde la pantalla de
    opciones resuelve también ese caso.

  2. La ruta /{alias}.
  - La ruta queda limitada a un solo segmento alfanumérico
    (/{alias:[A-Za-z0-9]+}). Así no captura /index.html, /swagger-ui/...,
    /v3/api-docs ni /css/..., porque tienen punto, guion o más de un segmento.
  - Con eso solo no alcanza. Las rutas fijas de un segmento siguen pudiendo
    chocar con un alias: api, error (la usa Spring), v3, swagger. Spring les da
    prioridad a esas rutas, así que un alias que se llame igual quedaría
    inaccesible.
  - Por eso propongo una lista de palabras reservadas configurable, que el
    generador nunca use como alias.
  - Esto no adelanta D1. Los dos ejemplos de la consigna (xT3se, 15321) son
    alfanuméricos, así que cualquier formato que se decida entra en esa
    restricción.

  ## D1 – Formato y largo del alias

> que recomndas en cada minuta y porque? responde cada una

● Mi recomendación para cada duda de la minuta es la siguiente.

  D1 – Formato del alias → alfanumérico aleatorio, de 5 caracteres, sin
  caracteres ambiguos
  - Aleatorio y no secuencial: con números consecutivos (15321, 15322…)
    cualquiera puede probar valores y abrir enlaces de otros, que suelen ser
    carpetas privadas de Drive.
  - Alfanumérico: con 5 caracteres da unos 550 millones de combinaciones, contra
    100.000 si fuera solo numérico. Y como los enlaces duran 60 minutos, nunca
    hay tantos activos al mismo tiempo, así que 5 caracteres alcanzan de sobra.
  - Sin 0/O, 1/l/I: es más fácil de leer y dictar, que es lo que la consigna
    llama "memorizable".

  D2 – Misma URL dos veces → un alias nuevo cada vez
  - Cada pedido tiene sus propios 60 minutos, exactamente como dice la consigna.
  - Si se reutilizara el alias, el enlace de una persona dependería de lo que
    hizo otra. Por ejemplo, alguien recibe un enlace al que le quedan solo 2
    minutos.
  - Además es más simple, porque no hay que buscar duplicados.

  D3 – Enlace vencido o inexistente → página HTML simple con código 404
  - Quien abre la URL corta es una persona, desde el navegador o el celular al
    escanear el QR. Un mensaje en JSON o una pantalla en blanco no le dice nada.
  - 404 y no 410: el 410 significa "eliminado para siempre", y el alias puede
    volver a usarse.
  - Recomiendo no distinguir "vencido" de "inexistente". Es más simple y no
    revela información.

  D4 – Acortar una URL que ya es corta → rechazarla
  - Evita cadenas de enlaces cortos, e incluso bucles en los que un alias
    termina apuntando a sí mismo.
  - Tampoco tiene utilidad acortar algo que ya es corto.

  D5 – URL válida → absoluta, solo http y https, hasta 2048 caracteres, sin
  verificar que exista
  - Solo http y https: la consigna habla de "acceder vía HTTP/HTTPS", y bloquear
    otros esquemas evita usos maliciosos como javascript: o file:.
  - 2048 caracteres: es el límite práctico que soportan los navegadores.
  - No verificar que exista: obligaría al servidor a conectarse a cada URL, lo
    que la hace lenta y frágil. Además, una carpeta privada de Drive puede no
    responder al servidor aunque exista.

  D6 – Historial → no guardarlo
  - La consigna no lo pide y dice que el alias "podrá ser reasignado".
  - Sin historial, cada alias es una sola fila en la base, lo que simplifica el
    modelo y evita conflictos.
  - Si la Etapa 2 pide estadísticas o historial, el cambio queda acotado a un
    paquete.

  D7 – Dominio o IP → configurable en el servidor y en la extensión
  - El ejemplo de la consigna es una IP local (192.168.1.50) que cambia según la
    red donde se haga la demostración. Si quedara fija en el código, habría que
    recompilar cada vez.
  - Conviene preguntarle al docente dónde va a ser la demostración y si pide
    HTTPS. HTTPS cambia la configuración.

  D8 – QR → generarlo en el servidor
  - Hay una sola implementación y no dos, una en la web y otra en la extensión.
  - Se puede probar con tests automáticos en Java, que es parte del QA que pide
    la consigna.
  - Los clientes quedan más simples: solo muestran una imagen.
  - Ojo: la consigna dice textualmente que la web y el complemento "deben
    generar" el QR. Por eso es la duda en la que más importa confirmar con el
    docente. Si exige que lo genere el cliente, se usa una librería JavaScript
    en los dos.

  En resumen, cada recomendación cumple la consigna con la opción más simple,
  segura y fácil de cambiar después. Las que más conviene confirmar con el
  docente son D8, por la redacción literal, y D7, porque depende del entorno de
  la demostración.
